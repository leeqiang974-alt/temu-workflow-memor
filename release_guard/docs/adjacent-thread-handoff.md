# 给 398 表生成对话的交接指令

把下面整段复制到负责生成/修复 398 表的对话中。它不会让那个对话改变当前 398 源表，而是要求它为一个新的候选输出生成 Release Guard 证据。

```text
本批次必须接入项目中的 Temu Release Guard，不能把聊天结论、模型判断、J 非空、AC 与 J 同步或抽样检查当作发布批准。

目标：对当前 398 表生成一个新的候选输出副本，并为该副本生成完整证据包。禁止修改原始 398 表、原始图片、历史成功表或历史输出。

执行顺序：
1. 先复制原始 398 表到新的候选路径，并记录 batch_id、精确路径和 SHA-256 冻结值。
2. 把本次对话方案写成 proposal.json；只有我明确回复 `CONFIRM <proposal_id>` 后才能执行生表/生图。
3. 执行完成后生成 execution_receipt.json，记录所有输入和输出文件 SHA-256。
4. 生成 T1/角标人工审批文件，必须包含资产路径和资产 SHA-256。
5. 对每个物理行生成 J manifest，逐行包含：row、D、G、SKU货号、实际源图路径、生成 J、本地/OSS 资产、写入 J URL、AC previewImgUrls、匹配模式和警告。
6. 702/398 表的所有物理行必须逐行审计，不能只审样本或按 D 汇总。
7. 54 列必须逐格检查，并单独报告 JSON/54列链接、源图血缘、视觉审核状态和硬阻断项。
8. 导入/导出后重新读取候选表，生成 writeback_diff.json；任何受保护列变化都阻断。
9. 导入历史剔除 D 和错误素材锁；L095 必须硬校验：L095-00 只能使用 2\\2.png，L095-01 只能使用 3\\3.png。
10. 所有证据通过后，才运行：
   python -m release_guard --root <state_root> require-release <batch_id> <final_workbook>
11. 只有生成有效 release_certificate.json 后，才允许进入插件索引；否则明确报告 BLOCK，不得称为可提交。

最终回复必须分别报告：
- 表格结构状态
- 54列/JSON 链接状态
- J 逐物理行源图血缘状态
- 人工视觉审批状态
- 历史锁状态
- 写回差异状态
- Release Guard 状态
- 证书路径（若未生成，说明阻断原因）
```

## 两个对话的职责

- 398 表对话：生成候选表、图片、逐行 manifest、审批和差异证据。
- Release Guard：冻结哈希、验证证据、决定 BLOCK/PASS、生成证书、保护插件索引。

398 表对话不应直接说“已完成/可提交”；它必须以 Guard 的状态和证书为准。
