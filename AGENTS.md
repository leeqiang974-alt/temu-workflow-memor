# Temu Workbook Project Rules

## GitHub Durable Workflow Sync Gate

- Temu release-guard source, policies, schemas, tests, reusable skills, `AGENTS.md`, workflow Markdown, and stable user corrections are durable workflow assets. A local-only change is incomplete.
- Synchronize these assets to the configured GitHub memory/workflow repository after local verification. Record the repository, branch, commit, and pull-request URL when applicable.
- Keep generated workbooks, paid image binaries, credentials, caches, SQLite runtime state, and oversized review outputs out of GitHub. Commit source, policy, compact manifests, and audit summaries instead.
- When the active worktree contains unrelated edits or unresolved merges, publish through a clean worktree/branch and stage only the intended durable assets.
- A GitHub push does not make a workbook pass. Release status still comes only from the formal release guard and its certificate.

## Highest-Priority J Preview Zero-Trust Gate

- J preview matching is the highest-risk, penalty-sensitive field in this project. A non-empty J URL, a same-`L0xx` folder, matching SKU text, a same-D source, or `SKC属性.previewImgUrls == J` is never visual proof and must never be reported as a pass.
- Every physical row in every complete/new/refill workbook must have one immutable positive-evidence chain: exact `D` + row `G` + `SKU货号` + inspected source path + generated/local J asset + written J URL + AC `previewImgUrls`. Missing any link is a hard release block. A synchronized AC value only proves JSON consistency, not image correctness.
- Global review means all physical rows, not samples and not just grouped counts. It must separately report: 54-column/JSON linkage, source-asset lineage, visual review status, and hard blockers. Never collapse those categories into one green/pass count. Rows without a human or calibrated positive visual decision remain `待视觉审`, not `通过`.
- Count/quantity/spec claims (`2格`, `3格`, `2联`, `3联`, `2个`, `3个`, `15`, `30`, etc.) are always visual claims. They are forbidden from `unique-exact-sku-source-nonvisual-g`, same-D inheritance, filename scoring, or non-empty-J fallback. They require an explicit audited source mapping and sibling side-by-side review.
- L095 is the permanent sentinel failure: `L095-00 -> ...\\2\\2.png`; `L095-01 -> ...\\3\\3.png`. The historical wrong mapping `L095-01 -> ...\\2\\2.png` must be blocked regardless of AC/AD/T consistency. User-confirmed bad D groups must be written to a machine-readable negative-evidence lock and must never re-enter as approved source evidence.
- A final workbook is blocked when any J row lacks exact positive source lineage or visual review. Do not upload J/T, write final OSS URLs, register the workbook, or describe it as submit-ready while the J zero-trust gate has blockers.

## YeahF Title And Fingerprint Rules

- Legacy YeahF 375/371 batches use a four-digit numeric fingerprint as the title search token. New final workbooks use a four-character uppercase alphanumeric fingerprint containing at least one letter and one digit (for example `A7K2`), appended at the end of the reconstructed Chinese title. Both formats are valid for lookup; the new mixed format increases the global registry capacity and avoids treating normal English words as a code.
- Mode split: for an explicit request to **regenerate/rebuild titles and four-digit fingerprints**, create a new unique four-digit numeric fingerprint per exact D for that output file. Remove source/vendor D-like codes, old trailing fingerprints, HTML, and URLs from the Chinese title before appending the new code. For a repair/writeback that says to preserve titles, recover the confirmed existing fingerprint instead.
- The legacy three-character letter-digit-letter tracking code belongs to a different 189-D historical workbook. Do not apply it to the YeahF batch and do not replace the original four-digit fingerprint with it.
- When rebuilding a YeahF title, keep the exact-D mapping in an auditable `D -> title -> four_digit_fingerprint` index. Same exact D must have the same title; do not mention row-level G variants in a group-level title unless every row in that exact D shares it.
- Never use one generic title template for all D values in one L0xx. Each exact D needs its own reconstructed title, based on its own source title/specification/features; title-body duplication across different D values is a failure even if fingerprints differ.
- Verify title work by checking: all effective D have exactly one valid trailing fingerprint, fingerprints are unique across exact D and all registered final workbooks, same-D title mismatch is zero, no legacy three-character code remains, and reconstructed titles are normally 70-80 characters excluding whitespace.

- A paid production image runner must be closed-loop: `submit -> query result -> immediate download -> decode/size check -> SHA-256 -> durable local manifest`. A submission-only script is forbidden for production batches.

- Treat provider image URLs as short-lived. Download immediately when a task first reports success. Never leave successful provider URLs for a later manual retrieval stage.
- Use a bounded in-flight window, default maximum 8 paid tasks. A single generation failure or isolated download failure must not stop unrelated tasks: mark that exact D failed/recovery-pending, free or quarantine its slot, continue the remaining queue, and never auto-resubmit it.
